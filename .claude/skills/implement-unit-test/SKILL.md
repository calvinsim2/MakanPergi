# Implement Unit Test

## Purpose

Find functions that have not been covered by Unit Tests, and write test cases for them - consisting of positive and negative cases.

Support two modes:

- `audit`: Find and report functions that have not implemented a full unit test and which file they are in (with code lines) without changing files.
- `fix`: Find functions that have not implemented a full unit test, apply safe fixes, and build the affected solution.

Interpret `$ARGUMENTS` as follows:

1. The first argument is the mode: `audit` or `fix`.
2. Any remaining argument is the file, folder, project, or solution scope.
3. If no mode is supplied, use `audit`.
4. If no scope is supplied, inspect the entire current repository.

Before starting, read the applicable `CLAUDE.md` files and follow all project-specific instructions.

## Definition of Full Unit test

A isolated function is considered to have full unit test when:

1. There are at least ONE positive and negative case for the function.
2. All lines in the function are to be covered by unit test.

## Positive Test case

A positive test case are defined as follows:
1. No exceptions occured, or the portion of code covered does not encounter an `Exception` or `ApiException`
2. For Controllers (etc, CuisineController.cs), positive test case are defined by having status code of 2xx (for example: 200, 201).
3. For functions (or API payloads) that returns an `IEnumerable<>` or `List`, the test case is considered as POSITIVE if there is at least ONE item in the collection returned.

## Negative Test case

Negative test case are defined as follows:
1. Exceptions occured, or the portion of code covered encounter an `Exception` or `ApiException`
2. For Controllers (etc, CuisineController.cs), negative test case are defined by NOT having a status code of 2xx (for example: 400, 500).
3. For functions (or API payloads) that returns an `IEnumerable<>` or `List`, the test case is considered as NEGATIVE if there is NO item in the collection returned.


## Unit Test Files Location and Naming Convention

Unit Test files are STRICTLY to be written into `MakanPergiTest` project.

Files are to be segregated in the same structure as the actual segregation done in the actual project. 

For example:

MakanPergiWebApi
 - Controllers
   - CuisineController.cs
   
and functions resides in CuisineController.cs: 
   
```
  csharp
    [HttpGet]
	public async Task<ApiResponse> GetAllCuisineViewModel()
	{
		try
		{
			List<CuisineDataModel> cuisineDataModels = (await _cuisineService.GetAllCuisineAsync()).ToList();
			List<CuisineViewModel> cuisineViewModels = _mapper.Map<List<CuisineViewModel>>(cuisineDataModels);

			return new ApiResponse("CuisineViewModels fetched successfully", cuisineViewModels);
		}
		catch (Exception ex) 
		{
			throw new ApiException(ex.Message);
		}
	}
	
	[HttpGet("{id:guid}")]
	public async Task<ApiResponse> GetCuisineById(Guid id)
	{
		if (id == null || id == Guid.Empty)
		{
			throw new ApiException("Id is empty", StatusCodes.Status400BadRequest);
		}

		CuisineDataModel cuisineDataModel = await _cuisineService.GetCuisineByIdProcessAsync(id);

		CuisineViewModel cuisineViewModel = _mapper.Map<CuisineViewModel>(cuisineDataModel);

		return new ApiResponse("Cuisine fetched successfully", cuisineViewModel, StatusCodes.Status200OK);
	}
  
```

Then, the structure of these unit tests for these functions that are to be added into `MakanPergiTest` should be:

MakanPergiTest (project)
 MakanPergiWebApiTest (folder)
  - Controllers (folder)
    - CuisineControllerTest.cs


Naming Convention of files are to be: <file name where the application logic/function resides> + 'Test'.cs

Based on the example functions above, since GetAllCuisineViewModel() and GetCuisineById(Guid id) are in the same file,
their unit test should be written in the same file: CuisineControllerTest.cs

### Unit Test code structure

From top:
- Required mocked data for A.CallTo
- A.CallTo calls
- Actual function call
- Assert (perferably asserting values returned from the function)

Naming convention for unit test should be <FunctionName>_<Positive or Negative>_<Scenario>_<Expected result>

Example
Application logic:

```csharp
[HttpGet]
public async Task<ApiResponse> GetAllCuisineViewModel()
{
    try
    {
        List<CuisineDataModel> cuisineDataModels = (await _cuisineService.GetAllCuisineAsync()).ToList();
        List<CuisineViewModel> cuisineViewModels = _mapper.Map<List<CuisineViewModel>>(cuisineDataModels);

        return new ApiResponse("CuisineViewModels fetched successfully", cuisineViewModels);
    }
    catch (Exception ex) 
    {
        throw new ApiException(ex.Message);
    }
}
```

Unit test structure:

```csharp
[Fact]
public async Task GetAllCuisineViewModel_Negative_NoCuisineExists_ShouldReturnEmptyList()
{

    List<CuisineDataModel> cuisineDataModelMock = new List<CuisineDataModel>();

    A.CallTo(() => _cuisineServiceMock.GetAllCuisineAsync()).Returns(cuisineDataModelMock);

    ApiResponse? result = await _cuisineController.GetAllCuisineViewModel();

    ApiResponse viewResult = Assert.IsType<ApiResponse>(result);

    List<CuisineViewModel> cuisineViewModels = Assert.IsAssignableFrom<List<CuisineViewModel>>(viewResult.Result);

    Assert.Equal(StatusCodes.Status200OK, viewResult.StatusCode);
    Assert.Empty(cuisineViewModels);
}
```

## Variable and Instances naming rules

Variable and Instances names are to be appended with a 'mock' on top of their initial naming to allow easier understanding 
that the data is a mocked instance or mock data.

Examples:

- `List<CuisineDataModel> cuisineDataModelsMock = new List<CuisineDataModel> { cuisineDataModelMock };`  
- `private readonly ICuisineService _cuisineServiceMock = A.Fake<ICuisineService>();`
- Only actual calls that are not mocked are exempted from this rule.
  For example: `private readonly CuisineController _cuisineController;`


## Safety rules

Only write the test cases in `MakanPergiTest` Project

Do not change or write into other Projects.

Do not change any existing application logic codes.

Avoid amending application logics when their existing logic have cases that is not possible to test. Report them for manual review.

Do not introduce or download new packages, should one be needed, report them for manual review.

## Audit mode

When running in `audit` mode:

1. Do not modify any file.
2. Search all files in the requested scope.
3. Report each problem with:
   - file path
   - line number
   - current code
   - recommended replacement
   - reason
4. Group the results into:
   - safe automatic fixes
   - manual-review items
5. Report the total:
   - files scanned
   - violations found
   - safe fixes
   - manual-review items

## Fix mode

When running in `fix` mode:

1. Inspect the requested scope.
2. Ensure the functions each have a positive and negative cases minimally, and all of the lines are covered by tests.
3. Do not modify manual-review items.
4. Review the resulting diff.
5. Verify that placeholders and arguments match.
6. Run `git diff --check` when the repository uses Git.
7. Follow the build instructions from `CLAUDE.md`.
8. If no build instructions exist:
   - locate the relevant `.sln` or `.csproj`;
   - run `dotnet build` on the narrowest appropriate solution or project.
9. Do not commit the changes.

## Final report

After completing the task, report:

- scope inspected
- files scanned
- files changed
- Functions that have new unit tests implemented
- manual-review items
- build command used
- build result
- any remaining logging analyzer warnings
- a concise summary of the Git diff
